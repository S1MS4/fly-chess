## 2. What this session found (all in the README now)

- **The first eye was blind on 12 squares** and couldn't tell piece types apart on 33 (`docs/img/eye_coverage.png`). Cause: ranks of hex1 and hex2 taken separately, and the eye is a tilted oval in those coordinates. Fix: `eye_input(c, "fair")` in `flychess/io_maps.py`, cut by equal shares of R1 to R6 cells along hex1+hex2, then hex1-hex2. Old flies keep `"ranks"` (a checkpoint only works with its eye); `--eye fair` in train_dl/train_bio/train_cached. Probe: 18.8% vs 17.7% top-1, loss 3.015 vs 3.026 (within probe noise of about 0.01 to 0.015).
- **ChessBench labels every winning move 100%.** In won positions all 8 candidates read 100.0, so the fly can't learn to mate. 40 replayed games: vs random 2-18-0, all 18 draws with the fly a rook or more up (9 repetitions, 3 stalemates, 3 fifty-move, 2 move cap, 1 insufficient); vs greedy 0-19-1 (10 insufficient material, 6 repetitions, 3 fifty-move). `runs/draws-dl.json`. Fix: `scripts/make_curriculum.py` (111,911 decided + 11,100 endgames, Stockfish depth 12, mate in N = 10000 - 100 N cp, 100 cp = 2.5 points of "win%"), `--curriculum 0.1`.
- **Backprop through time explodes about 11x per step from step 7 back** (`docs/img/blame.png`, `tools/bptt.py`): neurons the board hasn't reached have zero calibration spread, so homeostasis gives them gain 25. ## 5. Gotchas found this session

- **WSL sets `NAME` to the computer's name** (`LAPTOP-LG4EHQEM`). `NAME=${NAME:-dl-day}` in a script silently used it: the first day run wrote to `runs/LAPTOP-LG4EHQEM`. The driver uses `RUN`/`FLY_RUN` now.
- **4 GB on the GPU at once doesn't work here.** A `tf.Variable` filled slice by slice OOMed (slice assignment reads the whole variable first), and putting it there as 12 constants took the whole WSL VM down (uptime reset, every process gone, no traceback). `train_cached.Fitter` streams 344 MB blocks instead. When a run dies with no traceback, check `uptime` in WSL.
- The day run restarted at 05:05 after both of those; extraction (2.3 h) didn't have to be redone. A memory watchdog (session scratchpad `memwatch.sh`, log `memwatch.log`) stops train_cached if WSL's available memory falls under 700 MB; `tools/heat_guard.py` does the same from now on (`--min-memory`), but the guard running now is the older one.
- A readout step on cached rates costs about the same at batch 1,024 and 8,192 (fixed overhead, measured next to the run: 22 vs 35 ms). Phase A's fit runs at 1,024 (3.7 min a pass over 3M positions); train_cached's default is 8,192 with lr 2e-3 now, so Phase B's refits (a new process) use that. `step`/`score` run with `autograph=False`, so editing train_cached.py can't break a running fit any more.
- Don't edit `scripts/train_day.sh` while it runs: bash reads a running script as it goes.
- **The heat guard's pauses vs timeouts.** A SIGSTOP doesn't stop the clock: anything with a wall-clock timeout fails when it resumes. python-chess's `engine.play` waits 10 s plus the move time, so `StockfishPlayer.move` now starts a fresh engine on `TimeoutError` (tested with a script that SIGSTOPs a game for 15 s: a fresh engine took over and the game went on). Keep that in mind for anything new with a timeout.
- **A crash with a python-chess engine open never exits** (its event loop thread isn't a daemon and waits for the engine): `rating.py` closes engines in `finally` now, and the drivers run the rating under `timeout 2h`.
- **Downloads break.** `scripts/download_chessbench.py` retries 5 times (30 s to 8 min apart); `train_cached` Phase B skips a file it still can't get and stops only after 5 failures in a row. `tests/test_download_retry.py` (run it with `python tests/test_download_retry.py`: the venv has no pytest).
- `tools/watch.py` warns when the log has been quiet for 45 minutes; it used to show the last line ("Elo games") for 9 hours as if all was well.
- **Check for a spinning nvcontainer when the CPU runs hot.** The NVIDIA App's SPUser telemetry container (`nvcontainer.exe ... plugins\SPUser`) got stuck at 100% of a core for over a day. `Get-Counter '\Process(nvcontainer*)\% Processor Time'`; it's the user's own process (no admin), the NVIDIA container restarts it fine. Arijus approved stopping it once (2026-10-20); ask again next time.
- nvidia-smi's utilization and power read inside a throttled run come from the end of a working phase, so they look like flat out (97%, 60 W). Judge the throttle by speed and temperature instead.
